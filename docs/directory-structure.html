Project Structure

a-piece-of-art 추천 디렉토리 구조

사용자용 웹(Next.js)과 서버(FastAPI + 서버 렌더링 CMS)를 한 저장소에서 관리하는 구성입니다. 두 앱은 언어가 달라 폴더로만 분리하고, OpenAPI 스키마로 타입을 공유합니다.

front: Next.js (별도 담당자 구성) FastAPI · Python 3.12+ · uv SQLAlchemy 2.0 (async) · Alembic CMS: Jinja2 + HTMX AWS Amplify · ECR · ECS Fargate RDS PostgreSQL · Parameter Store S3 + CloudFront + Route 53 (이미지) GitHub Actions

서버 프로세스는 1개입니다

api/와 cms/는 서버 두 대가 아니라, FastAPI 앱 하나 안에서 URL 접두사(prefix)로 나눈 라우터 두 개입니다. server/app/main.py에서 둘을 함께 등록하므로 서버 프로세스 하나로 /api/v1/*와 /cms/*가 모두 동작합니다.

server/app/main.py
from fastapi import FastAPI
from fastapi.staticfiles import StaticFiles

from app.api.v1.router import api_router
from app.cms.router import cms_router

app = FastAPI()
app.include_router(api_router, prefix="/api/v1")   # JSON API — front가 호출
app.include_router(cms_router, prefix="/cms")      # CMS HTML 화면 — 관리자가 접속
app.mount("/cms/static", StaticFiles(directory="app/cms/static"), name="cms-static")
terminal
$ cd server && uv run fastapi dev app/main.py   # 이 명령 하나로 API와 CMS가 함께 뜸

로컬 개발 시 실행하는 프로세스는 아래 3개입니다.

역방향 import는 금지합니다. 예를 들어 services/가 api/를 import하면 안 됩니다. 그래야 같은 서비스를 API와 CMS 양쪽에서 부를 수 있습니다.

도메인 기반(feature) 구조로 가지 않은 이유 — 초기에는 도메인이 작품·작가·사용자 정도라 계층 구조가 더 찾기 쉽습니다. 도메인이 10개를 넘어가면 app/domains/artwork/{models,schemas,service,router}.py 형태로 전환을 검토하세요.

CMS 구성 방식

"FastAPI + CMS 화면"이라는 요구에 맞춰 서버 안에 CMS를 두는 방식을 추천합니다.

방식위치장점단점
A. Jinja2 + HTMX 추천 server/app/cms/ 배포 단위 1개, 서비스 로직 직접 호출, JS 빌드 없음, 화면 자유도 높음 복잡한 인터랙션(드래그 정렬, 에디터)은 JS 추가 필요
B. SQLAdmin server/app/cms/admin.py 모델만 등록하면 CRUD 화면 즉시 생성 커스텀 화면·워크플로 구현이 어렵고 디자인 제약
C. 별도 Next.js 앱 cms/ (루트) front와 같은 기술로 풍부한 UI 앱 3개 관리, CMS 전용 API 추가 필요, 초기 비용 큼

A 방식에서 CMS 화면은 JSON 대신 HTML을 돌려주는 FastAPI 라우트입니다. 목록 필터·페이지 이동은 HTMX로 _rows.html 같은 조각만 교체하므로 SPA에 가까운 사용감을 얻을 수 있습니다.

빠른 시작이 필요하면 초기에는 B(SQLAdmin)로 /cms/db에 기본 CRUD를 붙여두고, 작품 등록처럼 자주 쓰는 화면만 A 방식으로 직접 만드는 혼합도 가능합니다. 둘 다 app/cms/ 아래에 두면 구조가 유지됩니다.

API 계약 · 타입 공유

Python 스키마가 원본이고, TypeScript 타입은 생성해서 씁니다.

→

서버는 /openapi.json을 항상 최신으로 유지하고, front는 이 파일로 타입을 생성해서 씁니다. 스키마가 바뀌면 front에서 필드명 오타나 누락이 타입 에러로 드러납니다. 호환이 깨지는 변경(필드 삭제·이름 변경)은 front 담당자와 미리 공유합니다.

front — Amplify 설정

Amplify는 GitHub 저장소에 직접 연결되면 push할 때마다 스스로 빌드합니다. GitHub Actions에서 CI를 먼저 통과시킨 뒤 배포하려면 Amplify 브랜치의 자동 빌드를 끄고, Actions에서 start-job으로 빌드를 요청해야 합니다. 자동 빌드를 켜두면 push 한 번에 빌드가 두 번 돕니다.

amplify.yml (저장소 루트)
version: 1
applications:
  - appRoot: front
    frontend:
      phases:
        preBuild:
          commands:
            - corepack enable
            - pnpm install --frozen-lockfile
        build:
          commands:
            - env | grep -e NEXT_PUBLIC_ >> .env.production   # Amplify 환경변수를 Next.js 빌드에 전달
            - pnpm run build
      artifacts:
        baseDirectory: .next
        files:
          - '**/*'
      cache:
        paths:
          - node_modules/**/*
          - .next/cache/**/*
.github/workflows/front-deploy.yml (요약)
on:
  push:
    branches: [main, develop]
    paths: ["front/**", "amplify.yml"]

jobs:
  ci:
    uses: ./.github/workflows/front-ci.yml   # front-ci.yml에 workflow_call 트리거 추가 필요
  deploy:
    needs: ci
    runs-on: ubuntu-latest
    permissions:
      id-token: write                        # OIDC 토큰 발급
      contents: read
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ vars.AWS_DEPLOY_ROLE_ARN }}
          aws-region: ap-northeast-2
      - run: >
          aws amplify start-job
          --app-id ${{ vars.AMPLIFY_APP_ID }}
          --branch-name ${{ github.ref_name }}
          --job-type RELEASE
front 담당자와 합의할 부분: 위 amplify.yml은 pnpm 기준 예시이므로, front 담당자가 정한 패키지 매니저와 빌드 명령에 맞춰 수정합니다. 또한 Amplify Hosting은 SSR을 지원하는 Next.js 버전 범위가 정해져 있습니다. create-next-app을 실행하기 전에 Amplify 문서에서 최신 Next.js(16) 지원 여부를 확인하고, 아직 지원하지 않으면 지원되는 메이저 버전으로 고정하세요.

server — ECR · ECS 설정

.github/workflows/server-deploy.yml (요약)
on:
  push:
    branches: [main, develop]
    paths: ["server/**", "infra/ecs/**"]

permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: ${{ github.ref_name == 'main' && 'prod' || 'dev' }}   # GitHub Environment별 Variables 사용
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ vars.AWS_DEPLOY_ROLE_ARN }}
          aws-region: ap-northeast-2
      - uses: aws-actions/amazon-ecr-login@v2
        id: ecr

      - name: 이미지 빌드 · 푸시
        run: |
          IMAGE=${{ steps.ecr.outputs.registry }}/a-piece-of-art-server:${{ github.sha }}
          docker build -t $IMAGE server
          docker push $IMAGE
          echo "IMAGE=$IMAGE" >> $GITHUB_ENV

      - uses: aws-actions/amazon-ecs-render-task-definition@v1   # 태스크 정의에 새 이미지 주입
        id: td
        with:
          task-definition: infra/ecs/task-definition.${{ vars.APP_ENV }}.json
          container-name: server
          image: ${{ env.IMAGE }}

      - name: DB 마이그레이션
        run: ./scripts/ecs-migrate.sh ${{ steps.td.outputs.task-definition }}

      - uses: aws-actions/amazon-ecs-deploy-task-definition@v2
        with:
          task-definition: ${{ steps.td.outputs.task-definition }}
          cluster: ${{ vars.ECS_CLUSTER }}
          service: ${{ vars.ECS_SERVICE }}
          wait-for-service-stability: true

migrate 서비스 교체 전에 실행

ecs-migrate.sh는 새 태스크 정의를 등록하고, 명령만 alembic upgrade head로 바꾼 일회성 태스크를 실행한 뒤 종료 코드를 확인합니다. 실패하면 배포를 멈춥니다.

migrate 컨테이너 시작 시 실행 금지

태스크가 여러 개면 시작할 때마다 마이그레이션이 동시에 돌 수 있습니다. 컬럼 삭제처럼 호환이 깨지는 변경은 배포를 두 번으로 나눕니다.

OIDC 액세스 키 저장 안 함

Actions는 OIDC로 IAM 역할을 임시로 넘겨받습니다(assume). GitHub에는 역할 ARN, 클러스터명처럼 비밀이 아닌 값만 Variables로 둡니다.

파일명에 UUID를 쓰면 같은 키에 다른 이미지를 덮어쓸 일이 없습니다. 이미지를 교체하면 새 키로 올리고 DB 키를 바꾸므로 CloudFront 캐시 무효화(invalidation)가 필요 없고, 캐시 TTL을 길게(예: 1년) 잡을 수 있습니다.

storage_service — 로컬과 운영을 같은 코드로

server/app/services/storage_service.py (요약)
class StorageService:
    async def upload(self, upload: UploadedFile, prefix: str) -> str:
        key = f"{prefix}/{uuid4()}{Path(upload.filename).suffix.lower()}"
        if self.backend == "s3":
            # boto3는 동기 라이브러리라 스레드풀에서 실행
            await run_in_threadpool(
                self.s3.upload_fileobj, upload.file, settings.s3_bucket, key,
                ExtraArgs={"ContentType": upload.content_type or "application/octet-stream",
                           "CacheControl": "public, max-age=31536000, immutable"},
            )
        else:
            # 로컬: server/media/ 에 저장, main.py에서 /media 로 서빙
            await run_in_threadpool(self._save_local, upload.file, key)
        return key                              # DB에는 이 키만 저장

    def url(self, key: str | None) -> str | None:
        return media_url(key)                   # 운영: https://img.example.com/…

로컬에서는 STORAGE_BACKEND=local로 두고 main.py에서 app.mount("/media", StaticFiles(directory="media"))를 등록합니다. 운영에서는 Parameter Store 값으로 s3와 https://img.example.com이 들어가므로 코드 변경 없이 S3와 CloudFront를 씁니다.

front에서는 API가 내려준 image_url을 그대로 쓰면 됩니다. next/image를 쓴다면 img.example.com과 localhost:8000을 허용 도메인으로 등록해야 하며, 이 내용은 front 담당자 전달 사항에 포함되어 있습니다.

보안 버킷은 비공개

S3 퍼블릭 액세스는 모두 차단하고, 버킷 정책에서 해당 CloudFront 배포(OAC)의 s3:GetObject만 허용합니다. S3 URL로 직접 접근하면 403이 떨어져야 정상입니다.

인증서 CloudFront는 us-east-1

img.example.com용 ACM 인증서는 서울이 아니라 버지니아 북부(us-east-1)에서 발급해야 CloudFront에 연결됩니다. ALB 인증서와 헷갈리기 쉽습니다.

IAM 권한은 최소로

ECS 태스크 역할에 arn:aws:s3:::버킷/artworks/*, …/artists/* 경로의 PutObject, DeleteObject만 줍니다. 읽기는 CloudFront가 하므로 서버에 필요 없습니다.

front 이미지 최적화 비용

next/image는 Amplify에서 리사이즈할 때 연산 비용이 듭니다. 트래픽이 커지면 업로드 시 서버에서 썸네일(예: 400·1200px)을 미리 만들어 두는 방식을 검토하세요.

대용량 원본을 올리게 되면 CMS 업로드가 ECS를 거치므로 수십 MB 이상 파일은 느려질 수 있습니다. 그때는 서버가 발급한 Presigned URL로 브라우저가 S3에 직접 올리고, 완료 후 키만 서버에 알리는 방식으로 바꾸면 됩니다. storage_service 인터페이스는 그대로입니다.

주의 값 변경 후 재배포

파라미터 값은 태스크가 시작될 때만 읽습니다. 값을 바꿨다면 aws ecs update-service --force-new-deployment로 태스크를 새로 띄워야 반영됩니다.

IAM 실행 역할과 태스크 역할 구분

파라미터를 읽는 건 태스크 실행 역할(ssm:GetParameters, kms:Decrypt)이고, S3처럼 앱이 쓰는 권한은 태스크 역할에 둡니다.

front 서버 쪽 비밀값이 필요할 때

Amplify의 Secret 기능을 쓰고, 빌드 단계에서 .env.production에 기록해야 Next.js SSR 런타임에서 읽을 수 있습니다. NEXT_PUBLIC_ 접두사는 절대 붙이지 않습니다.

로컬 규칙: .env는 git에서 제외하고, 키 목록만 적은 .env.example을 커밋합니다. 운영 비밀값을 로컬 .env에 복사하지 않습니다. 로컬은 docker-compose의 PostgreSQL을 씁니다.

초기 세팅 순서

이 문서 기준으로 뼈대를 만드는 순서입니다.

  1. 루트 정리 샘플 main.py를 지우고 git init, .gitignore, .editorconfig, README.md를 만듭니다.
  2. front 자리 잡기 front/index.html 하나만 두고 커밋해서 폴더를 git에 올립니다. 이후 front 담당자가 index.html을 지우고 프로젝트를 생성합니다.
  3. server 생성
    terminal
    $ mkdir server && cd server && uv init --app --python 3.12
$ uv add "fastapi[standard]" "sqlalchemy[asyncio]" asyncpg alembic pydantic-settings jinja2 python-multipart boto3
$ uv add --dev pytest pytest-asyncio ruff
$ uv run alembic init -t async alembic
  4. 로컬 인프라 docker-compose.yml에 PostgreSQL을 띄우고, server/.env.example에 DATABASE_URL, SECRET_KEY, STORAGE_BACKEND, MEDIA_BASE_URL 등 키 목록을 적어둡니다.
  5. 연결 확인 GET /api/v1/health와 /cms 로그인 페이지 하나를 만들고, front에서 health API를 호출해 끝까지 연결되는지 확인한 뒤 기능 개발을 시작합니다.
  6.
